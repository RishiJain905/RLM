The goal

A Recursive Language Model never reads a long input directly. The input sits in a Python REPL as a context variable; the model writes code to inspect it and calls itself on pieces of it, then returns the answer with submit().

We build it in two parts: train the root model with RL, then build the harness it runs in. The trained model becomes the harness's default root.

Part 1: RL training of the root

Goal: a LoRA that beats the base model at probing context, decomposing, using sub-calls when code alone can't, and submitting a correct answer.

Task suite

Answers live in context. Some tasks must need reading comprehension so sub-calls matter. Keep pass rate in the 20-80% band.

Now: toy tasks; datasets being researched

RL environment

REPL subprocess, metadata-only first message, truncated output, limits on turns and sub-calls.

Now: working prototype (rlm_rl/archive/rlm_env.py)

Reward

Correctness on submit, small penalties for no submit, syntax errors, budget overruns.

Now: prototype in the env

RLSD update

Teacher is the same checkpoint with a sibling's code or env feedback in context, never the gold answer.

Now: working via logprob injection

Training infra

W&B serverless, CISPO, group size 8, concurrency cap 8, token ids rebuilt from prompt logprobs.

Now: working (notebooks 01-03)

Evaluation

Held-out tasks, including longer contexts than training. Accuracy, sub-calls per episode, leakage.

Now: 48 episodes; grow to 100+

Part 2: the RLM harness

Goal: one small loop that runs any Python-writing chat model as an RLM, tuned for ours, and later does real agentic work through Claude Science-style primitives.

Model-agnostic by interface

One OpenAI-compatible client. Per-model profiles hold context size, chunk guidance and batching hints; the loop and bridge never change.

Batched sub-calls from day one

llm_batch with a host-side concurrency limit. The paper's runs were all sequential.

Sandbox in two steps

Subprocess kernel with timeouts first, Docker with network off later. The bridge is the only way out.

Logging is a feature

Every turn and bridge call, with token ids and logprobs, so transcripts can be re-scored and reused for RL.

How the two parts connect

Same contract

The RL environment is a narrow version of the harness core: REPL, context, sub-calls, submit, truncation, budgets. It already serves sub-calls over a local HTTP endpoint. The env should call the harness loop rather than reimplement it.

The model learns the bridge API

Names, signatures, prompt format and truncation rules from training are what the model expects at inference. Today the env says llm_query and the harness design says llm. Freeze one API before the production run.

Logs feed training

Harness logs carry exact token ids and logprobs, so real harness transcripts can become future RL data.

Integration milestone

Serve the LoRA behind an OpenAI-compatible endpoint, plug it in as the root, and compare it with the base model inside the full harness.
