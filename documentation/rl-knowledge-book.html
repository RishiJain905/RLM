Reference · RL post-training

RL post-training, from one GPU to a cluster

How policy-gradient RL is run on a large language model, and what it costs in memory, hardware and care. Part 1 is the practical route, LoRA on one GPU or a serverless service. Part 2 is full fine-tuning, the way large labs usually build it. Then a side-by-side comparison and a guide for choosing.

Start here

How to read this book

It is written for someone who knows machine learning and has run an RL job, but is still learning the systems underneath: where the weights live, which process generates text, which one trains, and what has to move between them. Every chapter stands alone, so jump in from the contents.

Three conventions keep the numbers honest. Boxes tagged Our run report what happened in prod-v2, a 27B run on W&B Serverless RL. A figure with ≈ in front of it is a typical or computed value, not a measurement. Everything else is general knowledge about how these systems are usually built. Colours mean the same thing in every diagram:

  • LoRA adapter, the small trained piece
  • Sampler, generates rollouts
  • Trainer, fully trained weights
  • Frozen base or reference
  • Reward and verifiers

The short version

  • An RL episode returns one number. That is little information, so a small LoRA adapter can absorb it, and research on LoRA for RL found it matches full fine-tuning even at very low ranks.
  • On one GPU the frozen base is loaded once and shared by the sampler and the trainer. The adapter is about 100 MB. The KV cache of long episodes, not the adapter, decides what fits.
  • The sampler and the trainer must agree on token probabilities. Watch their correlation (probs_corr) and keep the pass rate in a learnable band.
  • Full fine-tuning updates every weight. With Adam in mixed precision that is about 16 bytes per parameter, so a 27B model needs about 430 GB of training state before activations, and the sampler fleet must receive the new weights after every update.
  • Choose by what you have: one GPU, a service, or a cluster. The decision flowchart near the end does it in three questions.

1.1 · Foundations

What RL post-training is

RL post-training starts from a language model that can already do the task a little, and pushes it toward replies that score well. Nobody supplies the right answer. The model tries, the attempt is scored, and attempts that scored better than their peers are made more likely.

Policy
The model being trained, written πθ. At each position it gives a probability for every possible next token.
Rollout (episode)
One complete attempt. The model reads a task and writes a reply, or runs a multi-turn exchange with tools, and the attempt ends with a reward.
Reward
One number for the whole attempt, from a test suite, an exact-match check, a rule or a judge model.
Group
Several rollouts of the same task. Our run used six per task.
Advantage
How much better a rollout did than its group. In GRPO-style methods it is the reward minus the group mean, divided by the group's spread. There is no separate value network to train, which saves a model's worth of memory.
Reference model
The frozen starting model. A KL penalty keeps the policy from wandering far from it.

Advantage, worked on one group

Take one task with six rollouts, two of which pass. The group mean reward is 0.33 and the spread (standard deviation) is 0.47. Each rollout's advantage is its reward minus the mean, divided by the spread, so passes get about +1.41 and failures about −0.71.

The update

Every token in a rollout gets its rollout's advantage. The gradient raises the probability of those tokens when the advantage is positive and lowers it when negative. Because the tokens were sampled a moment ago, the update weighs each token by an importance ratio: the probability the model gives it now, divided by the probability it had when it was sampled. The ratio is near 1 when nothing has moved.

// per token t, in a rollout with advantage A ρ_t = π_θ(token_t) / π_sampler(token_t) PPO : loss_t = −min( ρ_t·A , clip(ρ_t, 1−ε, 1+ε)·A ) CISPO : loss_t = −stopgrad( clip(ρ_t, ...) ) · A · log π_θ(token_t) total = mean(loss_t) + β · KL( π_θ || π_ref )

PPO's clip stops the gradient for any token whose ratio has left the band (ε is often about 0.2), so one batch cannot drag the policy far. CISPO, introduced with MiniMax-M1, clips the importance weight instead and treats it as a constant, so every token still contributes a gradient, including rare tokens that a PPO clip would drop. Both are sketches here; libraries differ in details such as how the average over tokens is taken.

The KL term is the average gap between the policy's and the reference's log-probabilities on the sampled tokens. A small coefficient β keeps the model close to where it started, which protects its general abilities.

1.2 · LoRA

LoRA mechanics

LoRA (low-rank adaptation) leaves each large weight matrix W untouched and learns a small correction beside it. The correction is the product of two thin matrices, B and A. The layer then computes

h = W·x + (α / r) · B·(A·x)

W is d_out × d_in and frozen. A is r × d_in and B is d_out × r, where the rank r is small, often 8 to 64. A starts as small random numbers and B starts at zero, so at step 0 the correction is exactly zero and the model equals the base. The scale α/r multiplies the correction; common choices set α to one to a few times r. Our run used r = 8 and α = 32, a scale of 4.

Size grows linearly with rank

An adapted matrix adds r × (d_in + d_out) parameters, so the total is r times a constant that depends on which matrices you adapt. As an illustration with made-up dimensions, a 5,120 × 5,120 projection holds 26.2 million weights, and a rank-8 adapter on it holds 81,920, about 0.3% as many. For our 27B model, adapting all the linear layers costs about 6.8 million parameters per unit of rank, which is about 13.6 MB per unit of rank in bf16 (2 bytes each).

Target modules

The usual choice is every linear layer: the attention projections (q, k, v, o) and the MLP projections (gate, up, down). Adapting only attention is cheaper but, in published comparisons, tends to lag, because the MLP holds most of the weights. If you can only afford one knob, spend it on covering more layers before raising rank.

1.3 · Capacity

Why low rank is enough for RL

Supervised fine-tuning (SFT) shows the model the answer. Every token of the target is a label, so one example carries hundreds or thousands of tokens the weights must learn to reproduce. An RL episode returns one number. Whatever that number says about a 3,000-token reply, it says it about the reply as a whole: better than the group, or worse. The information arriving per episode is on the order of a bit.

Thinking Machines tested this in LoRA Without Regret (2025). For RL they found LoRA matched full fine-tuning even at very low ranks. For SFT the picture differs. LoRA matches full fine-tuning while the dataset is small enough for the adapter to store, and falls behind once the data carries more information than the adapter has room for. SFT on a large dataset is where a higher rank pays off.

  • RL on a narrow behaviour: a low rank such as 8 to 32 is usually plenty. Raising it mostly costs memory and checkpoint size.
  • SFT on lots of data: start higher, around 64 or more (approximate), and check against the loss on held-out data.
  • Learning rate: LoRA tends to want a larger learning rate than full fine-tuning, reported to be about ten times larger. That is why 1e-5 to 2e-5 is normal for LoRA RL at this size while full-FT RL often sits near 1e-6 (approximate).

1.4 · Systems

The one-GPU loop

On one GPU the sampler and the trainer are not two machines. They are two jobs that read the same copy of the frozen base. This arrangement is called colocating them. Because the base never changes, sharing it is safe, and the only thing that moves between the jobs is the adapter.

One step in four phases

  1. Rollouts. The sampler runs the base plus the current adapter and writes every episode in the step. It needs the KV cache, which grows with each token of each live episode. In multi-turn tasks it also waits on tools and verifiers.
  2. Score and KL. Verifiers produce rewards. The trainer runs a forward pass over the sampled tokens with the adapter on to get the policy's log-probabilities, then the same pass with the adapter off to get the reference's. No second model is loaded.
  3. Train. The backward pass runs through the whole base to reach the adapter's matrices, but only the adapter gets gradients and optimizer state. The memory this needs is activations, so the sampler's KV cache must be shrunk or released first. Some engines offer a sleep or offload mode for exactly this.
  4. Hand off. The updated adapter, around 100 MB, goes to the sampler. The next step's rollouts come from base plus the new adapter.

1.5 · Systems

The end of a step: what moves and what stays

After the last optimizer update of an RL step, five things need to be true before the next step starts. Most of them need no work at all, which is the point of the design.

The trainer
Already holds the new adapter. It trained those exact matrices in place, so nothing is copied back. Its optimizer state, the Adam moments, stays alongside and carries into the next step.
The sampler
Loads the new adapter in place of the old one. vLLM can load or hot-swap LoRA adapters without reloading the base, so the cost is a file of about 100 MB, not 54 GB. The next step's rollouts come from base plus the new adapter.
The base
Never changes. The sampler, the trainer and the KL reference all keep reading the same weights.
The KL reference
Stays the base with the adapter switched off, or a fixed earlier adapter if you want to anchor to a previous stage. It does not move each step. If it did, KL would only measure the last step's movement instead of the total drift.
The old adapter
Is kept as a checkpoint. Checkpoints are what you evaluate, compare and roll back to.

Our run

Each training step produced a new checkpoint named prod-v2:step<N>, and the next step's rollouts were sampled from that name. Before the rollouts began, a small warm-up call checked that the new checkpoint was actually being served. Checking first is cheap; discovering halfway through a step that rollouts came from the old adapter is not.

Pitfall: rolling back

In our earlier run (prod-v1) a rollback reloaded an old adapter with a fresh optimizer, and its first update was unusually large. A plausible reason: Adam rescales each step by running estimates of the gradient's size. With the estimates empty, the first updates are roughly the full learning rate on every parameter, whereas a warmed-up optimizer takes smaller steps on noisy ones. If you may need to roll back, save the optimizer state with the adapter. If you cannot, restart at a lower learning rate and ramp it up.

1.6 · Budgeting

Memory on one GPU for a 27B base

Four things share the card: the base weights, the adapter with its optimizer state, the activations of the training pass, and the KV cache that rollouts need. The base is the biggest fixed cost, and how you store it is your main choice.

bf16
2 bytes per weight, so ≈ 54 GB for 27B. No quantization error. The reference choice for quality.
8-bit
1 byte per weight, ≈ 27 GB. Saves half the memory. In bitsandbytes the int8 matrix multiplies are often slower than the 4-bit or bf16 paths, so measure before committing.
4-bit (QLoRA, NF4)
About half a byte per weight, ≈ 15 GB. The base is stored in NF4, a 4-bit format shaped for normally distributed weights, and each matrix is expanded to bf16 for its multiply. The adapter stays in bf16. This is QLoRA.

The KV cache is the item people underestimate. It stores the keys and values of every token of every live episode. Its size per token is 2 (keys and values) × layers × KV heads × head dimension × bytes per number. For a dense model in the 27B to 32B class with grouped-query attention that comes to roughly 0.2 to 0.4 MB per token in bf16 (approximate). At 0.3 MB, one 16,000-token episode holds about 4.8 GB, and six at once hold about 29 GB. Long multi-turn episodes make this the deciding line in the budget. Storing the cache in FP8 halves it, and prefix caching shares the prompt across a group but not the replies that diverge after it. A model that mixes in linear-attention layers keeps a fixed-size state in those layers instead of a growing cache, so its real figure is smaller; our adapter's module names suggest Qwen3.8 is such a model (inferred).

  • One 80 GB card. An 8-bit base leaves comfortable room for sampling. A bf16 base fits but is tight: expect a few long episodes at a time, so shorten episodes, lower concurrency or store the KV cache in FP8. A 4-bit base leaves the most room but adds a dequantization step to every multiply.
  • A 24 to 32 GB card. Only a 4-bit base leaves any room to sample. Keep episodes short and few at once, or the sampler will queue and the step will be slow.
  • Rank. Raising rank grows the adapter and its optimizer state in line (chapter 1.2). At rank 64 that is about 7 GB, which is noticeable on a small card.

    1.7 · Correctness

    Sampler/trainer mismatch

    The sampler records the probability of every token it draws. The trainer later recomputes the probability of that same token. In theory they are the same number. In practice they come from two different programs: different kernels, different batching, sometimes different precision, so the numbers drift apart. The importance ratio ρ = trainer ÷ sampler then starts away from 1 before any learning has happened.

    Two things go wrong. The ratios become noisy, so clipping fires on tokens for the wrong reason. And the rollouts were drawn from a distribution slightly different from the one being updated, so the gradient is estimated from slightly wrong samples, which adds bias. A small gap is tolerable. A growing one corrupts training quietly, because the run still looks like it is working.

    How to watch it

    Track the correlation between the two probabilities across all tokens in a step. Our dashboard calls it probs_corr. It should sit very close to 1. Pick a gate in advance and stop or slow down when it falls below, instead of finding out from a bad eval.

    How to fix it

    • Make the two copies the same. Sample from the same quantized weights you train. If the trainer uses a 4-bit base, load that same 4-bit base in the sampler instead of a bf16 copy.
    • Correct for the gap. Use the sampler's recorded probabilities as the denominator of the ratio, and use importance-sampling corrections: truncate large weights, or drop tokens whose ratio is far from 1.
    • Use matching kernels. Where the framework offers deterministic or batch-invariant kernels, they make the two programs compute the same numbers.

    Ratios also move for a good reason

    If one RL step takes several optimizer updates on the same batch, later updates see a policy that has already moved, so their ratios differ from 1 even with a perfect sampler. That is expected, and the clip is there to handle it. Mismatch adds to that, which is why the check is on the correlation of the probabilities, not on whether any ratio equals 1.

    Our run

    In the earlier run (prod-v1), probs_corr fell to 0.969 to 0.975, below our 0.98 gate, and we cut the learning rate from 2e-5 to 1e-5. In prod-v2 at 1e-5 it stayed between 0.996 and 0.998.

    1.8 · Operating

    What to monitor, and the knobs

    An RL run can look healthy while learning nothing, or look broken while working. A handful of signals, read together every step, tell the two apart.

    Keep the pass rate in a learnable band

    A group only teaches something if it contains at least one pass and at least one failure. When every rollout in a group gets the same reward, every advantage is zero. If each rollout of a task passes independently with probability p, the chance that a group of six is mixed is 1 − p6 − (1 − p)6.

    The knobs

    • Learning rate. Commonly about 1e-5 to 2e-5 for LoRA RL at this size. Lower it first when KL climbs quickly or probs_corr falls.
    • Group size. Larger groups give a steadier baseline and more mixed groups, at a cost that grows in proportion. Ours was 6.
    • Rollouts per step. Tasks per step times group size. Ours was 6 × 6 = 36. More per step gives a smoother gradient and a slower step.
    • Task mix. The strongest lever on pass rate. Move it before touching anything else when the pass rate leaves the band.
    • KL coefficient and clip range. Keep the policy near the reference and limit how far one batch can move it.

    1.9 · Rewards

    Reward design and reward hacking

    The model optimizes the reward you wrote, not the one you meant. Anything cheaper than doing the task properly will be found eventually. Three habits keep this manageable.

    • Prefer verifiable rewards. Something you can run and check: tests pass, an exact match, a valid schema, a checker. It is less noisy than a judge's opinion and harder to argue with.
    • Add rule-based detectors that zero gamed rewards. Small programs that scan every episode for known tricks, such as editing the tests, hard-coding the expected output, or special-casing the test inputs, and set the reward to zero when one fires. They cost almost nothing and run on every episode.
    • Audit the wins. Periodically have a person or an LLM read a sample of high-reward episodes and look for tricks you did not anticipate. Read wins, not failures; failures rarely hide anything.

    Why audits must not feed the reward

    If an audit verdict becomes a reward signal, the model is trained to avoid being caught. That teaches it to hide the behaviour, not to stop. Use audits to change the tasks, the verifier and the detectors, and nothing else.

    1.10 · Where it runs

    Serverless vs local

    You can run this loop on a hosted service or on GPUs you control. The difference that matters most for LoRA is who chooses the rank.

    W&B Serverless RL (ART 0.5.20)

    • The service hosts the model and runs the training. You send rollouts and receive checkpoints.
    • Rank and alpha are fixed by the service. ART's register call sends only the model name, project and base model, so there is no setting for them to travel in.
    • No GPUs to manage, and no memory budget of your own to fit.
    • You pay for inference per step and wait on the service's speed.

    ART local backend, your GPUs

    • You run the sampler and trainer yourself, colocated as in chapter 1.4.
    • You choose the LoRA settings. ART's TrainableModel(lora_config={...}) is honoured by its local backend.
    • You own the memory budget (1.6), the mismatch checks (1.7) and the checkpoint handling (1.5).
    • Your cost is GPU time rather than a per-step bill.

    The practical consequence: if you want to test whether a higher rank helps, or which modules to adapt, you need the local backend. On the service you tune everything else, but rank is given.

    Part 2

    Full fine-tuning RL

    Every weight updates. This is how large labs typically build RL post-training, and it changes the shape of the system: a trainer cluster, a separate fleet of samplers, and a weight broadcast between them. What follows describes common architecture patterns. It makes no claim about any specific lab's internals.

    2.1 · Memory

    What a full fine-tuning trainer must hold

    With LoRA the trainer carries a frozen base plus a sliver of trainable state. With full fine-tuning every parameter is trained, so every parameter needs a gradient and optimizer state. The standard mixed-precision recipe with Adam keeps, for each parameter:

    • the weight in bf16 for compute, 2 bytes
    • its gradient in bf16, 2 bytes
    • an fp32 master copy of the weight, 4 bytes, which is where the small updates actually accumulate
    • Adam's first moment, 4 bytes, and second moment, 4 bytes

    That is about 16 bytes per parameter. Some stacks keep gradients in fp32 (20 bytes), and some shard or offload parts, but 16 is the usual planning figure. For 27B parameters that is about 430 GB before a single activation is stored.

    Sharding is what makes this workable. FSDP and ZeRO split the parameters, gradients and optimizer state across data-parallel GPUs and gather what each layer needs just in time. Spread over 8 × 80 GB, 432 GB is 54 GB per card, which leaves about 26 GB each for activations and communication buffers. For a model with 400 billion parameters the same arithmetic gives 6.4 TB of state, which is why frontier training is a cluster problem.

    Two more costs sit beside the trainer. The sampler fleet needs its own copy of the weights, 54 GB in bf16 at 27B, plus KV cache. And the KL term needs a reference model, either a frozen second copy (another 54 GB in bf16) or log-probabilities computed ahead of time.

    2.2 · Systems

    Architecture: trainer cluster, inference fleet, reward system

    At this scale the two jobs that shared a GPU in Part 1 become separate systems, each sized for its own bottleneck. Generation is memory-bandwidth bound and wants many replicas of an inference engine such as vLLM or SGLang. Training is compute and communication bound and wants a tightly connected cluster.

    Data parallel + sharding
    Each group of GPUs processes different sequences. FSDP and ZeRO also shard parameters, gradients and optimizer state across that group.
    Tensor parallel (TP)
    One weight matrix is split across GPUs, which exchange partial results inside every layer. It needs the fastest links, so it usually stays within a node.
    Pipeline parallel (PP)
    Consecutive layers sit on different GPUs and micro-batches flow through them like an assembly line.
    Megatron-style
    A trainer that combines data, tensor and pipeline parallelism (and expert parallelism for mixture-of-experts models) in one layout.
    Weight sync
    After an update the trainer sends the new weights to every sampler replica, usually with NCCL collectives over the cluster network. The trainer's sharded layout differs from each sampler's, so the weights are regathered and re-split on the way.
    Reference model
    A separate frozen copy for the KL term, kept on its own GPUs or replaced by precomputed log-probabilities.

    2.3 · Scheduling

    Synchronous vs asynchronous RL

    Rollouts take uneven time. Most episodes are short, and a few run very long. In synchronous RL the whole fleet generates with the current weights, waits for the last episode, then the trainer runs while the samplers sit idle, then the new weights go out. Every rollout is on-policy, which is clean, but the slowest episode sets the pace and both halves of the cluster take turns being idle.

    In asynchronous RL the samplers never stop. They keep generating while the trainer consumes whatever is ready, and the new weights reach them between episodes. A rollout may then have been drawn from weights a version or two old. That is off-policy data, and it is corrected with importance weights in the style of IMPALA's V-trace: weight each token by the ratio of the current policy to the policy that generated it, and truncate large weights to keep the variance bounded. Systems also cap staleness, dropping or down-weighting rollouts that are too old.

    Part 1's one-GPU loop is synchronous by construction: the same GPU cannot sample and train at once. Asynchrony is a luxury of having separate sampler and trainer hardware.

    2.4 · Numerics

    Precision: what can be small and what cannot

    Memory and speed both improve when numbers take fewer bits. The question is which numbers can afford it.

    • BF16 compute, FP32 master weights. The matrix multiplies run in bf16. The optimizer updates an fp32 copy and rounds it back to bf16 for the next forward pass. This is the 16-byte recipe from 2.1.
    • FP8 matmuls. Running the multiplies in 8-bit floating point roughly doubles throughput on hardware that supports it. DeepSeek-V3 trained with FP8 mixed precision, keeping the master weights and optimizer state at higher precision.
    • 8-bit optimizers. Quantizing Adam's two moments from 4 bytes to 1 byte each cuts the optimizer state about fourfold. At 27B that is 216 GB of moments down to about 54 GB.

    Why the weights themselves cannot live in 8 bits

    A weight update is tiny. With Adam, the change to a weight in one step is about the size of the learning rate, so around 1e-5. Floating-point numbers have gaps between neighbours, and when an update is smaller than half the gap, rounding returns the old value and the update vanishes. 8-bit values have large gaps. Even bf16 loses updates this small, which is why the fp32 master copy exists.

    Precision and the sampler/trainer mismatch

    The same issue from chapter 1.7 gets bigger at scale, because the sampler and trainer are different systems running different kernels, and the sampler is tempting to make cheaper. There are two broad answers.

    Match the numbers

    • Use batch-invariant or deterministic kernels, so the result for a token does not depend on how the batch was packed.
    • Or run the sampler at the same precision as the trainer.
    • Mismatch stays small. You pay in sampling speed.

    Cheaper sampler, then correct

    • Run the sampler in FP8 or another reduced precision, and fix the gap with importance-sampling corrections.
    • This is the approach Modal's 2026 post on mixed-precision samplers examines.
    • Sampling dominates the bill, so this saves real money. You pay in a larger gap to correct.

    The motivation is cost. That write-up reports that sampling takes about 80 to 85% of the GPU time in RL for Microsoft's MAI-Thinking-1. When generation is that much of the bill, making the sampler cheaper matters more than making the trainer faster.

    2.5 · Motivation

    Why labs do full fine-tuning anyway

    Given its cost, the reason to choose it is not obvious from the memory chart. Three reasons usually decide it.

    • Capacity for large behaviour changes. When post-training teaches many skills at once, from a large and varied pool of tasks, a rank-limited adapter can run out of room. Full fine-tuning has no such ceiling.
    • No adapter limits. No choice of rank, no choice of target modules, no learning-rate rule that differs from the rest of training. The same recipe used for pre-training and SFT carries over.
    • The weights are the product. A lab that ships a model ships its weights. A fully trained checkpoint is the artifact itself, with no base-plus-adapter pairing to manage in serving.

    The price is everything in this part: the 16 bytes per parameter, the trainer cluster, the sampler fleet, the weight broadcast and the numerics work. That price is why LoRA is the sensible starting point for anyone without a cluster.

    Decision guide

    Which route to take

    Start from what you have, not from what is fashionable. Three questions cover most cases.

    • If rank looks like the limit, raise it first. It costs a few hundred megabytes, not a cluster. Leave LoRA only when a higher rank still does not capture what the task needs.
    • If you are unsure, start with LoRA. It is cheap to try, it exposes the same RL problems (reward design, mismatch, collapse) that full fine-tuning has, and what you learn carries over.
    • If you run on a service, remember that rank and alpha are not yours to set. A rank experiment needs your own GPUs.

    Reference

    Glossary

    Rollout (episode)
    One complete attempt by the policy at a task, ending in a reward. Multi-turn tasks include the tool calls and observations in the middle.
    Group
    The set of rollouts drawn for the same task in one step. Their rewards are compared with each other.
    Advantage
    How much better a rollout did than its group. In GRPO-style methods it is the reward minus the group mean, divided by the group's standard deviation. Positive advantages raise token probabilities, negative ones lower them.
    KL (to the reference)
    The average gap between the policy's and the reference model's log-probabilities on the sampled tokens. It measures how far the policy has drifted and, as a penalty, limits the drift.
    CISPO / PPO clip
    Two ways to limit the importance ratio. PPO's clip stops the gradient for tokens whose ratio has left a band such as 1 ± 0.2. CISPO clips the importance weight itself, as a constant, so every token keeps a gradient.
    Importance ratio
    A token's probability under the policy being trained divided by its probability under the policy that sampled it. It is 1 when the two agree.
    LoRA rank / alpha
    Rank r is the inner width of the two thin matrices, and sets the adapter's size and capacity. Alpha sets the scale α/r applied to the adapter's output.
    QLoRA
    LoRA on top of a base stored in 4-bit NF4. The base is expanded to bf16 inside each multiply, and the adapter is trained in bf16.
    Colocate
    Run the sampler and the trainer on the same GPUs, sharing weights and taking turns. The alternative is separate sampler and trainer hardware.
    probs_corr
    The correlation between the sampler's recorded token probabilities and the trainer's recomputed ones. Near 1 means the two copies agree.
    Off-policy
    Learning from data produced by a different policy than the one being updated, for example stale asynchronous rollouts or a batch reused for several optimizer steps. Importance weights correct for it.
    KV cache
    The stored keys and values of every token already processed, kept so the model does not recompute them. It grows with each live episode's length.
