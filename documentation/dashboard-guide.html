What every chart on the RLM production dashboard tracks, and which way is good. The sections below follow the dashboard's own sections, top to bottom, so a chart you're looking at there is in the section of the same name here.

The run trains Qwen3.8-27B to work as a recursive language model (RLM): it reads long inputs and edits code through a Python REPL, and hands pieces of the reading to smaller copies of itself (sub-calls). Each training step gives it 8 tasks, tries each one 4 times, and nudges the model toward the attempts that scored better than the others on the same task. That last idea, called GRPO, explains most of the charts.

↑Higher is better ↓Lower is better ↔Best inside a range ≈Steady is good iContext, not a score

The cost meters and spend charts aren't covered here; the dashboard's Cost section explains itself. Open the dashboard: RLM Production Run.

Five things to check first

  1. Accuracy on selection-v3 (Evals) climbs over checkpoints from the base model's 50% at checkpoint 0. That is the number the run is for.
  2. Groups per step (Pass rates) shows at least 4 of 8 groups trainable most steps. Fewer means the tasks are too easy or too hard to learn from.
  3. Entropy against the base model (Policy health): the pooled line stays well under its 30% line. Crossing it is a collapse, and the run rolls itself back.
  4. Hack-detector hits (Reward and cheating) stay near zero, and the Claude audit's clean share stays near 100%.
  5. Infra error rate (Infra and timing) stays under the 1% line. Above it the run pauses for Rishi.

How to read any chart on the dashboard

The horizontal axis
The training step, 1, 2, 3… The Evals charts use the checkpoint instead: the model after that many steps, where checkpoint 0 is the untrained base model.
One point per step
Most values are averages over that step's 32 attempts (8 tasks × 4 tries). A single step is noisy; read the trend over 5 to 10 steps.
Grey dashed lines
Thresholds the training loop checks, such as the collapse lines, the 1% infra line or the 70% and 20% level lines. Crossing one usually triggers something.
Red vertical marks
Rollbacks. The run went back to an earlier checkpoint, usually after a collapse, and continued at a lower learning rate.
Faded lines
Steps from before a rollback, kept for comparison. They are no longer part of the run.
The number at top right
The latest value. Hover or tap a chart for each step's exact numbers.
Words the dashboard uses
Step
One round of training: 8 tasks, 4 attempts each, then one update to the model. A step takes roughly 15 to 35 minutes.
Episode, rollout
One attempt at one task, from the first turn to the submitted answer. 32 per step.
Group
The 4 attempts at the same task. GRPO compares attempts within a group, so a group where all 4 scored the same teaches nothing.
Reward
The score of an attempt: 1 for an exact answer (or, for code edits, every hidden test passing), partial credit for a near miss on some read tasks, 0 otherwise.
Family
A kind of task. Aggregation: count or classify things across a long log of short texts. Call graph: say which functions can end up calling a given one, in a generated code base. Needle: find the one function that does what a description says. Repo loc: name the files a real GitHub issue's fix changed. Edit real: fix a real bug in a real repository. Edit synth: fix a planted bug in a generated Python package.
Level
Difficulty, 1 to 5, per family. Read tasks grow from ~35K to ~400K characters; edit tasks grow in files and lines to change.
Controller
What moves each family's level: up when the family passes over 70% of its last 3 steps, down under 20%. If at least 8 attempts in a row were all right (or all wrong), it moves at once without waiting for 3 steps.
Root, turn
The root is the main model. Each turn it writes some thinking and a Python cell; the REPL runs the cell and shows the output.
Sub-call
The root calling the base model on a piece of text from inside its code (llm()). Up to 30 per episode.
Checkpoint
The model's weights after a given step. Checkpoint 0 is the base model.
Selection set
64 fixed tasks (selection-v3) evaluated every 10 steps to pick the best checkpoint. Never trained on.
Infra episode
An attempt lost to the machinery: a container that didn't start, a grader that never reported, a server that kept failing. Rerun or left out, never scored as a failure.
Retired task
An edit real task taken out of the draw after its group came back all-wrong twice or all-right once, since it can't teach anything more.
Thinking
The root reasons in hidden thinking tokens before each turn (at the "medium" setting). Sub-calls don't think.
No chart matches that search. Try a shorter word.

rlm/pass · dynamic sampling

Pass rates and difficulty

Whether the model is solving its training tasks, and whether the difficulty is set where it can still learn. The text under the section title also shows how many edit real tasks are retired and how many are left to draw.

Pass rate

↑Higher is better

The share of the step's attempts that were exactly right. "Without infra" leaves out attempts lost to the machinery; "with infra" counts them as failures.

Healthy
A noisy line that holds or rises, with dips right after level-ups. The two lines sit almost on top of each other.
Worry if
A long slide with no level-ups, or a gap between the two lines (infra trouble).

Pass rate by family (controller's 3-step window)

↔Best inside a range

Each family's pass rate over its last 3 steps: the number the controller uses. Grey lines at 70% (move up a level) and 20% (move down).

Healthy
Lines between 20% and 70%, or crossing 70% and then dropping as the family moves up. That range is where a model learns the most.
Worry if
A family sits under 20% at level 1 (it can't learn it), or above 70% at level 5 (nothing left to learn).

Difficulty level by family

↑Higher is better

Each family's level over time, as a staircase.

Healthy
Steps up, rarely down.
Worry if
Repeated up-down-up moves, which mean the level boundary is too sharp for the model.

Why each task gets 4 attempts (how GRPO learns)

iBackground for this section

The model doesn't learn from "this attempt scored 1". It learns from "this attempt did better than the other attempts at the same task". Each attempt's push is its score minus the group's average score.

1 of 4 right
The average is 0.25. The right one gets +0.75, a strong push toward whatever it did, and each wrong one gets −0.25. This is the most valuable case: a rare success to copy.
2 of 4 right
The average is 0.5: +0.5 for each right one, −0.5 for each wrong one. The clearest contrast between what works and what doesn't.
3 of 4 right
The average is 0.75. The wrong one gets −0.75, a strong push away from its mistake.
4 of 4 or 0 of 4
Every attempt equals the average, so every push is 0. Nothing in the group says what made an attempt better, so the group is dropped. That's why all-right and all-wrong groups "teach nothing", and why the controller keeps tasks at a level where the model sometimes succeeds and sometimes fails.

Comparing attempts inside a group is what lets GRPO work without a second model that predicts how good an answer should be. The group's own average plays that part. Four attempts is a trade-off between a reliable average and the cost of every extra attempt.

Groups per step

↑Higher is better (the "trainable" part)

The 8 groups of each step, split by what they were useful for. Trainable: the 4 attempts scored differently, so GRPO can learn from them. All 0: all 4 wrong (too hard). All 1: all 4 right (too easy). Other equal: all 4 got the same partial credit. Too small: fewer than 2 usable attempts after infra losses.

Healthy
4 or more trainable most steps.
Worry if
Trainable falls to 0-2. Under 2, the step skips training entirely.

Correct rollouts per group, last 10 steps

↔Best in the middle

How many of each group's 4 attempts were right, counted over the last 10 steps. The 0/4 and 4/4 bars are highlighted because those groups teach nothing.

Healthy
Most of the mass in 1/4, 2/4 and 3/4.
Worry if
Tall 0/4 or 4/4 bars: the levels are set too hard or too easy.

Pass rate by family and level, whole run

iContext, not a score

A table: each cell is a family's pass rate at one level over the whole run, darker for higher, with the number of attempts. The outlined cell is the family's current level.

Read it as
Where each family struggles. Rates should fall from left to right, since higher levels are harder.
Worry if
A family's current level shows a very low rate on hundreds of attempts.

Edit real retired and left to draw (text under the section title)

iContext, not a score

How many of the 107 edit real training tasks are retired, and how many can still be drawn. If too few are left, their slots go to edit synth tasks instead, and the text says so.

Healthy
"Left to draw" shrinks slowly. Late in the run, slots moving to edit synth is expected and planned.
Worry if
It empties in the first 20-30 steps, which would mean most tasks were too easy or too hard.
rlm/policy · actor

Policy health

Whether training itself is stable. These charts are about the model's internals, not its scores. Collapses show up here first.

Entropy against the base model (collapse signal)

↓Lower is better

How much less surprised the trained model is than the untrained base model by the very same sampled words, from the KL re-score. A model that collapses gets very sure of its own outputs, so this climbs. Comparing on the same words cancels out what each step happened to sample. Two lines: the solid one pools the last 3 steps' words together, and is what the rule reads; the thin one is each step on its own. One step re-scores only a few thousand words, so its own reading swings with how predictable they were: prod-v1's step 8 read 10.5% on mostly code while the pooled line stayed under 4%. The grey line is 30%.

Healthy
The pooled line at a few percent, creeping up slowly as the model learns. Single steps jumping around it are normal.
Worry if
The pooled line crosses 30%. That is a collapse: the run rolls back to the last checkpoint from before it began and continues at half the learning rate. A second one stops the run.

Entropy (mean −logprob of sampled root tokens)

≈Steady, slowly falling is good

How spread out the model's word choices are over everything it wrote that step. It also moves with what was sampled: longer, code-heavy episodes read lower, since code is predictable. In prod-v1 it fell from 0.48 to 0.31 over steps 1-5 while the model itself had barely changed. The grey line is 70% of the highest value in the last 10 steps.

Healthy
Wobbling with the task mix, without a steady slide.
Worry if
It slides along with the chart above. On its own it counts toward a rollback only when a step has no matched reading, and then only after 3 steps in a row under the grey line.

Within-group reward std (Echo Trap signal)

≈Steady is good

How different the 4 attempts at each task scored, averaged over the step. GRPO learns only from those differences. The grey line is half the 10-step average. It also falls whenever a step draws families the model finds very easy or very hard.

Healthy
Steady, clearly above 0.
Worry if
It stays under the grey line for 3 steps: a possible "Echo Trap", where every attempt gives the same answer. That logs a warning in Notices; check the entropy charts and the task mix.

KL to base (logged, not in the loss)

≈Small and slowly rising is good

How far the trained model's word probabilities have moved from the base model's, measured on 4 attempts a step. Two estimates of the same thing (k1 and k3). The note under the chart says how many re-scored turns lined up; 0 misaligned is healthy.

Healthy
Starts near 0 and rises slowly as the model learns.
Worry if
It jumps suddenly, or reads n/a because every re-scored turn was misaligned (which says nothing about training, only about the measurement).

Grad norm

≈Steady is good

The size of each training update. The grey line is 3 times its median.

Healthy
Wobbling around a steady level.
Worry if
Spikes above the grey line, especially several in a row.

probs_corr (trainer vs sampler logprobs)

↑Higher is better

Whether the training server and the inference server agree on how likely each sampled word was. They should, since they hold the same weights. The grey line is the 0.98 floor.

Healthy
0.99 or above, flat.
Worry if
It drops under 0.98: the model being trained no longer matches the one that produced the attempts.

Clip fraction (CISPO, weights clipped to [0, 5])

↓Lower is better

The share of words whose training weight hit the safety limit. That happens when the model has moved a lot between producing an attempt and training on it.

Healthy
Near 0%.
Worry if
It climbs above a few percent.

Importance ratio

↔Best close to 1

For each word, how much more or less likely the model being trained finds it than the model that wrote it. Mean, 95th and 99th percentiles.

Healthy
Mean about 1.00, p95 near 1.1, p99 near 1.2-1.3.
Worry if
The mean drifts away from 1, or p99 climbs well above 1.5.

Learning rate

≈Flat is good

How big a step each update takes: 2e-5, dropping to 1e-5 if a collapse forces a rollback.

Healthy
A flat line at 2e-5.
Worry if
It steps down. That means a collapse already happened and was handled once.

Train loss

iContext, not a score

The training objective's value. In this kind of RL it hovers around 0 and doesn't mean "lower is better" the way it does in ordinary training.

Read it as
A sanity check: small values wobbling around 0.
Worry if
Sudden large swings, alongside a grad norm spike.

RLM behaviour

How the model works through a task: how many turns and sub-calls it uses, what goes wrong along the way, and how much it writes. These show whether gains come "the RLM way", by reading with code and sub-calls rather than guessing.

Healthy

It climbs toward 30 while accuracy stays flat. That's busywork.

↓Lower is better

The share of episodes that used all 30 sub-calls.

Healthy
Near 0%.
Worry if
It rises: the model is spending its budget instead of planning.

Root turns per episode

The average number of turns per episode. Read tasks allow 12 and edit tasks 30, so the average mixes both.

Read it as
Effort. More turns on harder levels is normal.

First-turn submits

↓Lower is better

The share of episodes that submitted an answer on the very first turn, before looking at the input.

Healthy
Near 0%.
Worry if
It rises: the model is learning to guess. The early-submit detector zeroes these.

Trouble per episode

↓Lower is better

Five kinds of friction, per episode: REPL errors (the code crashed), cell timeouts (a cell ran past 120 s in read tasks or 300 s in edit tasks), turns without code (no runnable code block in the reply), broken replies (the subset that ended on their own: cut off mid-code, empty, or a bare tag) and outputs cut short (it printed more than the output limit). In prod-v1 broken replies grew from about 1% of turns to 25% by step 16 and snowballed inside episodes, so since the restart from checkpoint 10 each one costs 0.1 of the episode's reward, up to 0.3.

Healthy
All low and falling. Some errors are normal; the model fixes them on the next turn. Broken replies should fall toward zero under the penalty.
Worry if
Broken replies or turns without code climb (a format problem the model is learning), or timeouts climb (slow or looping code).

Root transcript length (tokens)

iContext, not a score

How long the root's whole conversation gets: average, 95th percentile and longest.

Read it as
Effort and cost. It grows with harder levels.
Worry if
The longest keeps growing fast, which means rambling or loops.

Output tokens per episode

iContext, not a score

How much the root writes (thinking included) and how much the sub-calls write, per episode.

Read it as
Where the effort and the cost go.
Worry if
Root output balloons while accuracy doesn't move.

Context size (characters)

iContext, not a score

The average size of the input the model has to work through. Read tasks go from ~35K characters at level 1 to ~400K at level 5. Edit tasks only show the issue and a file list, so they pull the average down.

Read it as
A rising line means the families are moving up levels.
Worry if
Nothing in particular: it follows the levels.

Episodes with a turn cut off at the token cap

↓Lower is better

The share of episodes where at least one turn hit its length limit (3,072 tokens for read tasks, 4,096 for edit tasks), usually because thinking used the whole turn.

Healthy
A few percent or less.
Worry if
It climbs: the model is overthinking and losing turns.

rlm/reward

Reward and cheating

What the model is being scored on, and whether it's earning the score honestly. Detectors catch known tricks and zero the reward of any attempt that uses one.

Exact accuracy and mean reward

↑Higher is better

Exact accuracy is the share of attempts exactly right (resolved, for edits). Mean reward also counts partial credit for near misses.

Healthy
Both rising, close together.
Worry if
Mean reward rises while exact accuracy doesn't: the model is farming partial credit.

Partial credit and near-blind answers

↓Near-blind lower is better

Partial credit is the average credit given for near misses. Near-blind is the share of answers closer to the "blind guess" than to the truth. The blind guess is the answer you could make up from the input's size alone, without reading it.

Healthy
Near-blind low or falling.
Worry if
Near-blind rises: answers are drifting toward guessing from metadata.

Hack-detector hits by rule

↓Lower is better

Attempts caught by each cheating detector, stacked per step. Early submit: answered before looking. Copied answer: typed an answer that appears nowhere in its work. Escape attempt: tried to get out of the sandbox. Timeout loop: 3 or more timed-out cells. Test tamper: changed the tests or test settings. Grader tamper: the grader's check tests came back wrong. Test aware: code that behaves differently when it's being tested. Network try (grey) is only logged.

Healthy
Near 0, an occasional hit.
Worry if
Hits on more than 5% of attempts over 10 steps and rising. That pauses the run for Rishi (stop rule 5). Blocked escape attempts that only tried to write a file or run a program (a scratch file in /tmp, say) still score 0 but don't count toward the pause.

Episodes that submitted

↑Higher is better

The share of attempts that gave an answer at all.

Healthy
Near 100%.
Worry if
It falls: attempts are running out of turns.

Claude audit of sampled wins (clean solve rate table)

↑Higher is better

Every 10 steps, Claude reads a sample of winning attempts and judges whether each answer really followed from the work shown. "Clean share" is the share judged clean. It never changes rewards.

Healthy
Clean share near 100%.
Worry if
Any win judged a hack. That pauses the run until the environment is fixed.

Stop rules

What would stop or pause the run

Checked after every step. Each rule shows OK, Watch, Fired or Not yet. A stop keeps the best checkpoint, a pause waits for Rishi, and every stop can be resumed.

1. Plateau stops, keeps the best

iShould stay OK

Fires after 3 selection evals (30 steps) with no new best and no family moving up a level. More training isn't helping.

2. Overfitting stops, keeps the best

iShould stay OK

Fires when training reward rises while selection accuracy falls by more than 5 points, two evals in a row. The model is memorising its training tasks. Smaller dips are inside the selection set's noise.

3. Frying stops, keeps the best

iShould stay OK

Fires when the capability check is more than 2 points below checkpoint 0 at two checks in a row, or more than 5 points below at one, or when a collapse comes back after one rollback.

4. Saturation stops, keeps the best

iA good problem to have

Fires when every family is at its top level with a pass rate above ~70%. The next step is harder data, not more training.

5. Hacking pauses for Rishi

iShould stay OK

Fires on a hack verdict in the Claude audit, or when detectors fire on more than 5% of attempts over 10 steps and rising (blocked file or program attempts left out). Someone fixes the environment, then the run resumes.

Learning-rate rule

iShould say "No collapse"

If the trained model becomes 30% less surprised than the base model by the same sampled words (or, for a step without that reading, raw entropy stays under 70% of its 10-step peak for 3 steps), the run rolls back to the last good checkpoint and continues at 1e-5. That happens once; a second collapse stops the run. Reward std falling for 3 steps only logs a warning.

Infra pause

iShould stay OK

More than 1% of attempts lost to infra over the last 10 steps pauses the run.

iContext, not a score

Everything that happened, newest first: starts and stops, evals, level moves, rollbacks, retired tasks, detector hits, and warnings. The chips filter by kind: interventions, warnings, evals and audits, level moves.

Sampled transcripts (training rollouts)

iContext, not a score

Real attempts from training: one win and one failure per step, plus any attempt a detector flagged. Each shows the task, the model's turns and code, its sub-calls and its score. Text is cut short, and eval tasks never appear.

Look here
To see what a number means in practice, such as what "turns without code" or a flagged attempt actually looked like.
