What every chart on the RLM production dashboard tracks, and which way is good. The sections below follow the dashboard's own sections, top to bottom, so a chart you're looking at there is in the section of the same name here.

The run trains Qwen3.8-27B to work as a recursive language model (RLM): it reads long inputs and edits code through a Python REPL, and hands pieces of the work to sub-calls, fresh calls to the base model made from inside its code. Each training step gives it 6 tasks, tries each one 6 times, and nudges the model toward the attempts that scored better than the others on the same task. That last idea, called GRPO, explains most of the charts. Until checkpoint 20 a step was 8 tasks tried 4 times on a different set of tasks; the card below lists everything that changed there.

Six things to check first

  1. Accuracy on selection-v4 (Evals) climbs from checkpoint 20, its first point. It replaced selection-v3 at the task shift, and it is the number the run is for now.
  2. Right answers that delegated (RLM behaviour) rises, and Tasks solved without sub-calls falls. Getting the model to hand work to sub-calls is what the task shift is for.
  3. Groups per step (Pass rates) shows at least 3 of 6 groups trainable most steps. Fewer means the tasks are too easy or too hard to learn from.
  4. Entropy against the base model (Policy health): the pooled line stays well under its 30% line. Crossing it is a collapse, and since the run is already at its lowest learning rate, it now pauses the run for Rishi.
  5. Hack-detector hits (Reward and cheating) stay near zero, and the Claude audit's clean share stays near 100%.
  6. Infra error rate (Infra and timing) stays under the 1% line. Above it the run pauses for Rishi.

NewWhat changed at checkpoint 20

At checkpoint 20 sub-calls were flat, about 0.3 an episode and nearly all in aggregation, and 3 to 6 of each step's 8 groups came back all solved. The run stopped there, with no rollback, and resumed at step 21 on new task families built so that handing work to sub-calls pays. On 2026-10-19 it also moved to a new W&B model holding the same weights (branch 3), because W&B had stopped serving the old one.

How to read any chart on the dashboard

The horizontal axis
The training step, 1, 2, 3… The Evals charts use the checkpoint instead: the model after that many steps, where checkpoint 0 is the untrained base model.
One point per step
Most values are averages over that step's attempts: 36 from step 21 (6 tasks × 6 tries), 32 before. A single step is noisy; read the trend over 5 to 10 steps.
Grey dashed lines
Thresholds the training loop checks, such as the collapse line, the 1% infra line or the level lines. Crossing one usually triggers something.
Red vertical marks
Rollbacks: the run went back to an earlier checkpoint (twice to checkpoint 10, over broken replies) and carried on from there. The mark at step 20 is the move to a new W&B model with the same weights; nothing was undone.
Faded lines
Steps a rollback threw away (branch 0's steps 11-16 and branch 1's steps 11-12), kept for comparison. They are no longer part of the run.
Step 20
The task shift. Lines by family end or start there, and most behaviour charts change level. See the card above.
The number at top right
The latest value. Hover or tap a chart for each step's exact numbers.
Words the dashboard uses
Step
One round of training: 6 tasks, 6 attempts each (8 and 4 through step 20), then one update to the model. Through step 20 a step took roughly 15 to 35 minutes.
Episode, rollout
One attempt at one task, from the first turn to the submitted answer. 36 per step from step 21, 32 before.
Group
The attempts at the same task: 6 from step 21, 4 before. GRPO compares attempts within a group, so a group where all scored the same teaches nothing.
Reward
The score of an attempt: 1 for an exact answer (or, for code, every hidden test passing), partial credit for a near miss on some read tasks, 0 otherwise. From step 21 a right answer that really delegated gets up to 0.2 more.
Family
A kind of task. From step 21: Context search (named aggregation on the dashboard): count or classify lines across a long log of short texts, where every question needs 1,500 to 4,100 lines labelled, more than the root can read itself. Research: answer a question that takes several hops, or list every answer, from a corpus of Wikipedia text. Build from a spec (edit spec): write a set of linked Python functions whose bodies were removed, from a requirements document. Find and fix (edit bugs): find and fix several linked planted bugs, given only the failing tests. Through step 20 also: callgraph (which functions can end up calling a given one), needle (find the function a description matches), repo loc (name the files a real GitHub issue's fix changed), edit real (fix a real bug in a real repository) and edit synth (fix a planted bug in a generated Python package).
Level
Difficulty, 1 to 5, per family. Context search grows from ~35K to ~400K characters; research from ~250K to ~1.2M characters and from 2 to 4 hops; the coding families from 1-3 functions or bugs in one file to up to 12 functions or 7 bugs across up to four files.
Controller
What moves each family's level: up when the family passes over 70% of its last 3 steps, down under 30% (20% through step 20). If at least 8 attempts in a row were all right (or all wrong), it moves at once without waiting for 3 steps.
Root, turn
The root is the main model. Each turn it writes some thinking and a Python cell; the REPL runs the cell and shows the output.
Sub-call
The root calling the base model on a piece of text from inside its code (llm(), or llm_batch() for several at once). Up to 80 per episode from step 21, 30 before.
Delegated
On the dashboard's charts, an attempt delegated if it made at least one sub-call. The bonus uses a stricter test: for read tasks, sub-calls that together read at least a quarter of the context; for coding, at least two sub-calls that each sent 1,000 characters or more. Failed sub-calls don't count.
Delegation bonus
Extra reward on a right answer that passed the stricter test: 0.2 at step 21, falling evenly to 0.1 at step 36 and to nothing after step 50. Wrong or hacked answers never get it, so the model can't earn it by delegating for its own sake.
Checkpoint
The model's weights after a given step. Checkpoint 0 is the base model.
Branch
Each restart from a checkpoint starts a new branch. Branches 1 and 2 restarted from checkpoint 10 after the broken-reply problem; branch 3 is the move to a new W&B model at checkpoint 20.
Selection set
Fixed tasks evaluated every 10 steps to pick the best checkpoint, never trained on. selection-v4 (47 tasks) from checkpoint 20; selection-v3 (64 tasks) before.
Infra episode
An attempt lost to the machinery: a container that didn't start, a grader that never reported, a server that kept failing. Rerun or left out, never scored as a failure.
Retired task
A coding task taken out of the draw after its group came back all wrong twice or all right once, or, from step 21, after it was solved without sub-calls, since it can't teach anything more.
Thinking
The root reasons in hidden thinking tokens before each turn (at the "medium" setting). Read-task sub-calls don't think; from step 21 coding sub-calls think at "low".
No chart matches that search. Try a shorter word.

ChangedWhy each task gets 6 attempts (how GRPO learns)

iBackground for this section

The model doesn't learn from "this attempt scored 1". It learns from "this attempt did better than the other attempts at the same task". Each attempt's push is its score minus the group's average score.

1 of 6 right
The average is 0.17. The right one gets +0.83, a strong push toward whatever it did, and each wrong one gets −0.17. This is the most valuable case: a rare success to copy.
3 of 6 right
The average is 0.5: +0.5 for each right one, −0.5 for each wrong one. The clearest contrast between what works and what doesn't.
5 of 6 right
The average is 0.83. The wrong one gets −0.83, a strong push away from its mistake.
6 of 6 or 0 of 6
Every attempt equals the average, so every push is 0, and the group is dropped. That's why all-right and all-wrong groups "teach nothing", and why the controller keeps tasks at a level where the model sometimes succeeds and sometimes fails.
With the bonus
2 of 6 right, one of them delegating, at step 21: scores 1.2, 1, 0, 0, 0, 0, average 0.37. The delegating win gets +0.83, the plain win +0.63, each wrong one −0.37. The bonus also splits an all-right group when only some of its wins delegated, so that group teaches "delegate" instead of being dropped.

Comparing attempts inside a group is what lets GRPO work without a second model that predicts how good an answer should be. The group's own average plays that part. Six attempts at 6 tasks (instead of four at 8) keep about the same number of episodes a step and make it likelier that a group is mixed, so fewer groups are wasted.

ChangedGroups per step

↑Higher is better (the "trainable" part)

The groups of each step (6 from step 21, 8 before), split by what they were useful for. Trainable: the attempts scored differently, so GRPO can learn from them. All 0: all wrong (too hard). All 1: all right with no bonus (too easy). Other equal: all got the same partial credit, or, from step 21, all were right and all earned the same bonus. Too small: fewer than 2 usable attempts after infra losses. A group where all were right but only some earned the bonus counts as trainable.

Healthy
3 or more of 6 trainable most steps.
Worry if
Trainable falls to 0-2. Under 2, the step skips training entirely, as branch 2's steps 16 and 20 did.

rlm/policy · actor

Policy health

Whether training itself is stable. These charts are about the model's internals, not its scores. Collapses show up here first.

ChangedEntropy against the base model (collapse signal)

↓Lower is better

How much less surprised the trained model is than the untrained base model by the very same sampled words, from the KL re-score. A model that collapses gets very sure of its own outputs, so this climbs. Comparing on the same words cancels out what each step happened to sample. Two lines: the solid one pools the last 3 steps' words together, and is what the rule reads; the thin one is each step on its own. One step re-scores only a few thousand words, so its own reading swings with how predictable they were: prod-v1's step 8 read 10.5% on mostly code while the pooled line stayed under 4%. The grey line is 30%. Since the move to branch 3 the rule reads only steps after 20.

Healthy
The pooled line at a few percent, creeping up slowly as the model learns. Single steps jumping around it are normal.
Worry if
The pooled line crosses 30%. That is a collapse. The run is already at 1e-5, the lowest rate the rule allows, so instead of rolling back it pauses for Rishi.

ChangedEntropy (mean −logprob of sampled root tokens)

≈Steady, slowly falling is good

How spread out the model's word choices are over everything it wrote that step. It also moves with what was sampled: longer, code-heavy episodes read lower, since code is predictable. In prod-v1 it fell from 0.48 to 0.31 over steps 1-5 while the model itself had barely changed. Expect a jump at step 21, with a new prompt and new tasks. The grey line is 70% of the highest value in the last 10 steps.

Healthy
Wobbling with the task mix, without a steady slide.
Worry if
It slides along with the chart above. On its own it counts toward a collapse only when a step has no matched reading, and then only after 3 steps in a row under the grey line.

ChangedWithin-group reward std (Echo Trap signal)

≈Steady is good

How different the attempts at each task scored, averaged over the step. GRPO learns only from those differences. The grey line is half the 10-step average. It also falls whenever a step draws families the model finds very easy or very hard. From step 21 the delegation bonus adds small differences inside all-right groups, so it can read a little higher until the bonus fades out after step 50.

Healthy
Steady, clearly above 0.
Worry if
It stays under the grey line for 3 steps: a possible "Echo Trap", where every attempt gives the same answer. That logs a warning in Notices; check the entropy charts and the task mix.

KL to base (logged, not in the loss)

≈Small and slowly rising is good

How far the trained model's word probabilities have moved from the base model's, measured on 4 attempts a step. Two estimates of the same thing (k1 and k3). The note under the chart says how many re-scored turns lined up; 0 misaligned is healthy. It can move at step 21, when the prompt and tasks changed; judge the trend after that.

Healthy
Starts near 0 and rises slowly as the model learns.
Worry if
It jumps suddenly, or reads n/a because every re-scored turn was misaligned (which says nothing about training, only about the measurement).

rlm/shape

RLM behaviour

How the model works through a task: how many turns and sub-calls it uses, what goes wrong along the way, and how much it writes. These show whether gains come "the RLM way", by reading with code and sub-calls rather than guessing. From step 21 the budget is 80 sub-calls and read tasks get 20 turns; the dashboard's own intro to this section still gives 30 and 12.

ChangedTrouble per episode

↓Lower is better

Six kinds of friction, per episode: REPL errors (the code crashed), cell timeouts (a cell ran past 120 s in read tasks or 300 s in coding tasks), turns without code (no runnable code block in the reply), broken replies (the subset that ended on their own: cut off mid-code, empty, or a bare tag, and stayed in the conversation), broken replies drawn again (next entry) and outputs cut short (it printed more than the output limit). In prod-v1 broken replies grew from about 1% of turns to 25% by step 16 and snowballed inside episodes, so since the second restart from checkpoint 10 (branch 2) they take no gradient: a win no longer reinforces them, and a loss no longer pushes down the ordinary words they're made of. From step 21 a sub-call prompt over 60,000 characters raises an error in the REPL instead of being cut, so REPL errors can rise while the model learns to split its reading.

Healthy
All low and falling. Some errors are normal; the model fixes them on the next turn. Broken replies should stay near zero.
Worry if

NewBroken replies drawn again (a line in Trouble per episode)

↓Lower is better

From branch 2's step 14, a broken reply in a training attempt is thrown away and drawn again, up to twice a turn, before it enters the conversation. The model never sees it, so it can't copy it, and it never reaches training. If the third draw is broken too, it stays, masked, and counts as a broken reply. This line counts the extra draws per episode, so it shows how often the model still ends a turn early. Evals keep one draw, so checkpoint scores stay comparable. On branch 2's steps 14-20 it read 0.5 to 1.8 an episode, while broken replies that stayed fell to about 0.3 or less.

Healthy
Falling slowly, with broken replies that stayed near 0.
Worry if
It keeps climbing: the model produces more broken replies, and each extra draw costs one more call. A lower learning rate is the next lever. Broken replies that stayed rising as well means even the third draw is failing.

rlm/reward

Reward and cheating

What the model is being scored on, and whether it's earning the score honestly. Detectors catch known tricks and zero the reward of any attempt that uses one.

ChangedExact accuracy and mean reward

↑Higher is better

Exact accuracy is the share of attempts exactly right (resolved, for code). Mean reward also counts partial credit for near misses and, from step 21, the delegation bonus. So mean reward can sit above exact accuracy while the bonus lasts, and the gap from the bonus closes by step 50.

Healthy
Both rising, close together.
Worry if
Mean reward pulls away from exact accuracy in a way the bonus can't explain (it is gone after step 50): the model is farming partial credit.

ChangedPartial credit and near-blind answers

↓Near-blind lower is better

Partial credit is the average credit given for near misses. Near-blind is the share of answers closer to the "blind guess" than to the truth: the answer you could make without really reading. From step 21 more answers earn partial credit. A research answer in words that doesn't match exactly scores 0.8 times its word overlap with the answer; a research list scores by its overlap with the true list; a context-search count that misses scores 0.8 × 0.75 for each unit it is off (a unit is 1, or 1% of the answer above 100). A research list's blind guess is what a plain search returns (every document naming the subject).

Healthy
Near-blind low or falling.
Worry if
Near-blind rises: answers are drifting toward guessing, or, on research, toward a search with no reading.

Hack-detector hits by rule

↓Lower is better

Attempts caught by each cheating detector, stacked per step. Early submit: answered before looking. Copied answer: typed an answer that appears nowhere in its work. Escape attempt: tried to get out of the sandbox. Timeout loop: 3 or more timed-out cells. Test tamper: changed the tests or test settings. Grader tamper: the grader's check tests came back wrong. Test aware: code that behaves differently when it's being tested. Network try (grey) is only logged.

Healthy
Near 0, an occasional hit.
Worry if
Hits on more than 5% of attempts over 10 steps and rising. That pauses the run for Rishi (stop rule 5). Blocked escape attempts that only tried to write a file or run a program (a scratch file in /tmp, say) still score 0 but don't count toward the pause.

Worry if
It falls: attempts are running out of turns.

Stop rules

What would stop or pause the run

Checked after every step. Each rule shows OK, Watch, Fired or Not yet. A stop keeps the best checkpoint, a pause waits for Rishi, and every stop can be resumed.

Changed1. Plateau stops, keeps the best

iShould stay OK

Fires after 3 selection evals (30 steps) with no new best and no family moving up a level. More training isn't helping. It counts selection-v4 evals from checkpoint 20.

Changed2. Overfitting stops, keeps the best

iShould stay OK

Fires when training reward rises while selection accuracy falls by more than 5 points, two evals in a row. The model is memorising its training tasks. Smaller dips are inside the selection set's noise. It compares selection-v4 evals, so it reads "Not yet" until there are enough of them.

3. Frying stops, keeps the best

iShould stay OK

Fires when the capability check is more than 2 points below checkpoint 0 at two checks in a row, or more than 5 points below at one, or when a collapse comes back after one rollback. "Watch" means the latest check was below checkpoint 0 but hasn't crossed a line yet.

Changed4. Saturation stops, keeps the best

iA good problem to have

Fires when every family in the mix (four from step 21) is at its top level with a pass rate above ~70%. The next step is harder data, not more training.

5. Hacking pauses for Rishi

iShould stay OK

Fires on a hack verdict in the Claude audit, or when detectors fire on more than 5% of attempts over 10 steps and rising (blocked file or program attempts left out). Someone fixes the environment, then the run resumes.

ChangedLearning-rate rule

iShould say "No collapse"

A collapse is the trained model becoming 30% less surprised than the base model by the same sampled words (or, for a step without that reading, raw entropy under 70% of its 10-step peak for 3 steps). At 2e-5 a collapse would have rolled the run back to the last good checkpoint and continued at 1e-5. The run has been at 1e-5 since step 11 (a decision after checkpoint 10, not a collapse), and 1e-5 is the floor, so a collapse now pauses the run for Rishi instead. Reward std falling for 3 steps only logs a warning.

ChangedInfra pause

iShould stay OK

More than 1% of attempts lost to infra over the last 10 steps (4 of 360 from step 21) pauses the run. After a resume the window counts as full, so one early error doesn't pause it.
