Teaching Qwen to recurse

We are about to train Qwen3.8-27B to answer questions about texts it never reads, and to change code in repositories too big to read. It gets a Python REPL holding up to ~400,000 characters, 12 turns, and 30 calls to a frozen copy of itself; for a coding task, a repository on disk, 20 turns, and tests it never sees that decide its score. This page walks the whole RL run end to end: what is built and tested, what the model actually sees, how every episode is scored and policed, how training decides when to stop, and what the run and the final eval will look like.

00 · OVERVIEW

The one-minute version

A Recursive Language Model (RLM) answers questions about a text too long to read in one go. Instead of pasting the text into the prompt, it keeps the text in a REPL variable and writes code to slice it, search it, and hand pieces to sub-calls. Part 1 of this project trains the model that writes that code, the root, with GRPO. Part 2 builds a general RLM harness whose default root is the trained LoRA.

Since 12 Oct the run also teaches the root to change code. Spec v2 gives 40% of the training tasks to two new edit families: the root gets a repository on disk and a bug to fix or a feature to build, and its change is graded by tests it never sees. The other 60% are the read tasks described first on this page. Chapter 09 shows what one of these edit episodes looks like.

01 · THE SETUP

A model that never reads the document

The RLM paper treats a long input as part of the environment rather than the prompt. The root model sees only metadata: the question, how big the text is, and its first three lines. Everything else it learns by running code. When a piece needs reading comprehension rather than str.count, it sends that piece to a sub-call: a fresh model call with no memory of the episode.

In our run, the root is Qwen3.8-27B with the LoRA we train. Every sub-call goes to the frozen base Qwen3.8-27B, so training improves how the root plans and delegates, not how well the reader reads. The four names the model can use are pinned in Bridge API v1, which the training environment and the Part 2 harness both import, so the model is trained on exactly the interface it will be deployed with.

03 · HOW WE GOT HERE
Why GRPO, and what it already learned

    
Before any production code, the project ran two small experiments to choose a training method. The three-way test counted customer messages and summed order records; the 20-step head-to-head used ticket tasks (support-ticket logs of 30-45K characters).

  

  

    

      
      
    

  

  

    
It learned the habit we want

    
On the hard tickets (the full log), the second half of GRPO's 20 steps looked different from the first. It stopped answering without looking, made more sub-calls, and got more right. On the easy tickets, which fit in the root's own reading, it kept answering directly in 68% of second-half episodes, and its reward on that family still rose to 0.92. It recursed where recursion pays, and not elsewhere.

  

  

    

      
      
    

  


  

    
What a trillion-parameter run taught a 27B one

    
In September 2026 Xiaomi streamed the RL post-training of MiMo-V2.6 live. Its scale is nothing like ours (1,568 prompts × 16 rollouts a step, against our 8 × 4), but its algorithm is the same kind, GRPO with mean-centred advantages and no std division, so its failures are the ones we would hit. Four of them shaped this build.

  

  

    

      
Incident
Models fetched the answer
Coding runs passed tests by pip install-ing a fixed release, curl-ing the fixed file, or git clone-ing a later commit.
Ours: no network, no git history, no project code in the sandbox (H2-H4). Edit episodes get a repository with one commit and nothing else to mine.

      
Incident
A silent infra failure
For ~3 hours, sandbox failures were scored 0 as if the model had failed. Flash rolled back to step 15.
Ours: every failure outside the model's control is an infra error and never reaches training (H5).

      
Incident
Saturated prompts
Some subsets hit 70-80% of prompts at 100% pass, which leaves GRPO nothing to compare.
Ours: a difficulty controller raises the level when a family passes above 70% (H13).

      
Practice
Zero hacks before the mean
A confirmed hack's reward is set to 0 before the group average, so it becomes a negative example rather than a win.
Ours: adopted as-is; try it in the GRPO calculator (H11).

    

  







  

    
04 · THE BOX
Four walls around code the model writes

    
Every cell the root writes runs as untrusted code. Each episode gets a fresh Docker container on WSL2 that is thrown away afterwards, and inside it three more layers stop anything the one before might miss. The only way out is a single Unix socket to the host's bridge, which accepts two requests: llm and llm_batch. submit never crosses it; its value returns with the cell's result.

    
This chapter describes the box a read episode runs in. An edit episode keeps the same outer walls but loosens two on purpose: the model may write its repository and run the repository's own programs. Chapter 10 lists exactly what changes.

  

  

    

      
      
    

  

  

    

      
Regression tests
52
At step 3, all passing in WSL2 in ~35 s. They try to read .env, the repo and /proc, reach the network and import project code.

      
32 at once
3-7 s
A step's worth of sandboxed test episodes, run in parallel; one container starts in 0.6-3.5 s. The 20-step run's steps took 150-390 s.

      
Secrets inside

The 64-bit task seed, the gold answer, the grader and the W&B key never enter the container (H3).

      
Leftovers after

Every test checks no container or episode directory is left behind (decision 3a).

    

  







  

    
05 · TRAFFIC
Thirty requests in flight, never thirty-one

    
A training step runs 32 episodes at once. Each root turn and each sub-call is one request to W&B's inference service, and up to 30 sub-calls per episode means a step can want hundreds at the same moment. Step 2 probed the service: it accepts exactly 20 requests in flight per model name, and answers the 21st with a 429. Root calls go to the training checkpoint (:stepN) and sub-calls to the base model (:step0), so the two can share 30.

  

  

    

      
      
    

  

  

    
When something breaks that isn't the model's fault

    
An episode that loses a sub-call to a 5xx after six tries, or whose container is killed from outside, says nothing about the policy. Scoring it 0 would teach the model to avoid whatever it happened to be doing, which is exactly MiMo's silent failure. So it is flagged with one of nine infra error kinds, logged, and dropped before advantages are computed.

    
rate_limitedserver_errortimeoutconnectionrejectedthinking_onbad_responsesandboxhost_bug

    
Too many of them pauses the run: above 1% of episodes in a single step during the second seed (one bad episode in 32 is 3.1%, so it pauses), and above 1% over the last 10 steps in production (4 of 320 would pause it). Errors the model causes itself, like its own crash, timeout or out-of-memory, stay the model's outcome. Every episode, eval included, is written to a JSONL transcript with the context stored only as its size and sha256 (H9).

  







  

    
06 · WHAT IT TRAINS ON
Six task families: four that read, two that edit

    
Every read task is generated on the host from a fresh random 64-bit seed, has one verifiable answer (a number, a name or a list, never multiple choice or a judge), and carries a blind guess so partial credit only pays for beating it. Each read family has five levels, from the ~36K characters of the old ticket tasks up to ~400K, which about 20 sub-calls of ~20K characters can cover. Cybersecurity was dropped from training on 11 Oct (decision 7c), and its share went to aggregation and code.

    
On 12 Oct, spec v2 cut the four read families to 60% of the tasks and gave the other 40% to two edit families, which ask the model to change code rather than answer a question (decision E-a). Both are built and tested: the read families in steps 3-8, the edit families in steps E2-E5. Chapters 09 and 10 explain the edit families.

  

  

    

      

        
aggregation · 25% · read
Count what the text is about

        
A log of short unlabelled texts, each with a date and a user id. The question lists 4-8 topics and asks for an aggregate: how many lines are about travel, which users wrote at least N about billing, which topics pass a threshold. Seven question kinds; two need no labels, so code alone answers them.

        
Text: CLINC150 30% · MASSIVE 20% · LEDGAR contract clauses 25% · arXiv titles 25%. OOLONG's method, rebuilt on permissive data. Was 45% before spec v2.

      

      

        
callgraph · 10% · read
Who can end up calling X?

        
A generated Python package of 15-60 modules with neutral names. The answer is every function from which a chain of calls reaches the target, scored by set-F1. From level 2, some calls hide from ast: aliases from level 2, dispatch tables from level 3, and getattr on string pieces from level 4.

        
Hidden calls rise from 0% to 50%; callers from 2-6 to 6-18. Blind guess: every function in the package. Was 20%.

      

      

        
needle · 10% · read
Find the function that does this

        
"Somewhere in this package is a function that adds up the squares of the even numbers in a list. What is it?" One exact name. Its look-alikes (odd items, cubes, a count) sit elsewhere in the package as decoys.

        
46 behaviours in 15 look-alike groups, each checked against a reference implementation. RepoQA's method. Was 20%.

      

      

        
repo_loc · 15% · read
Which files does the fix touch?

        
A real GitHub issue and its repository's Python files at the commit it was filed against. The answer is the set of files the real fix changed, scored by set-F1. Git history never enters the sandbox.

        
Long Code Arena bug localization: 531 training items from 37 repos. Blind guess: the files the issue names. Unchanged at 15%: finding where a change goes is the read skill closest to editing.

      

      

        
edit_real · 25% · edit
Built and tested
Fix the bug, or build the feature

        
A real repository with its own test suite, and a task: a reported bug to fix, or a described feature to implement. The change is graded by tests the model never sees. Permissive licences only. The first round trains on Python, Go and JavaScript repositories; Rust, TypeScript and Java follow in a later round.

        
Bug tasks (SWE-smith's for Python and Go), feature tasks we generate, and real-PR tasks from SWE-rebench V2: 107 training tasks in the first round, of about 310 planned. Levels by the size of the real fix. More in chapter 09.

      

      

        
edit_synth · 15% · edit
Built and tested
Change our generated packages

        
The packages behind callgraph and needle, with something to change: a bug to find from its symptom, a function to change along with every caller, or an option to thread through several modules. Hidden property tests grade it.

        
About a third of edit_real's cost per episode, and clean difficulty levels. More in chapter 09.

07 · THE SCORE
Partial credit that a guess can't earn

    
Every episode gets one number between 0 and 1, computed on the host. An exact answer earns 1. A wrong but close answer can earn up to 0.8, and this is where the old setup had a hole (H1): its near-miss credit was 0.8 × max(0, 1 − 4 × relative error), so on a big count, a guess from the line count alone landed close enough to score well without reading a line. The fix measures "close" against what a blind guess would get on that very task.

    

      
Numbers
0.8 × max(0, 1 − err / e_blind)
e_blind is the blind guess's own error on this task. Matching the guess earns 0.

      
Lists
0.8 × max(0, (F1 − F1_blind) / (1 − F1_blind))
Set-F1, rescaled so the blind strategy's F1 maps to 0.

      
Names
Exact or 0.
One function, user id or topic is either right or wrong.

    

    
Before any of that: no submit, or an answer that can't be parsed, is 0. After it: a hack detector that fires sets the reward to 0, and an infra error removes the episode altogether. Exact accuracy is logged beside the reward and is the headline metric.

    
All of this chapter is about read episodes. An edit episode has no answer to compare: its change is run against hidden tests and scores 1 or 0, with no partial credit (chapter 10).

  

  

    

      
      
    

  

  

    
Check before training (H1): passingA blind guesser scores no more than its exact-hit rate on every family and level. The step 8 red-team also tried cleverer guessers: the best fixed offset or subset earns 0.118-0.206 on tickets and aggregation and at most 0.011 on call graphs, against 0.53 and up for an honest reader who is off by one.

    
The near-miss formula has a dial, NEAR_MISS_SLOPE, kept at 1 (decision 5b). A logged-only diagnostic, near_blind, flags each wrong answer that sits closer to the blind guess than to the gold, so a policy drifting toward guessing shows up on the dashboard before it shows up in the reward.

  







  

    
08 · THE REFEREES
Detectors, an audit, and a red team

    
RL finds whatever the reward pays for, including things we didn't mean to pay for. Four rule-based detectors run on every read episode, and three of them on edit episodes too. When one fires, the reward becomes 0 before the group mean, so the hack is trained against rather than ignored. The rules were backtested on the 1,280 saved episodes of the 20-step run: none fired on any of them. Edit episodes add three more rules and one that only logs; they are in chapter 10.

  

  

    

      
early_submit
Answering without looking
Fires when submit() runs on turn 1, or before any code has read context.
The replay's guess on turn 1 scored 0.2318 and was zeroed.

      
copied_answer
Typing in an answer it never computed
Fires when the answer appears in the prompt, was typed into code, is distinctive (a number ≥100 or ≥3 characters), shows up in no REPL output, and isn't part of the task's own blind guess.

      
escape_attempt
Trying the walls
Fires on any audit event of kind network, file, process, ctypes, signal, tamper, host_import or malformed, or a bridge request the host refused.

      
timeout_loop
Burning the clock
Fires on 3 or more cell timeouts in one episode. Each timeout already wipes the REPL's variables.

    

  

  

    
What the red team found

    
Step 8 attacked the environment on paper and in tests, at $0. Its biggest finding was a detector hurting honest work: on repo localization and aggregation, copied_answer zeroed 13 of 104 honest wins, because a correct answer often is a name from the prompt (a file the issue mentions, a user id in the sample lines). The fix skips atoms of the task's own blind guess, since the reward already caps that guesser.

  

  

    

      
      
    

  

  

    
A second pair of eyes: the Claude audit

    
Rules only catch the cheats someone thought of. At every 10th checkpoint the training loop writes a sample of winning transcripts, and a Claude thread reads them against a written audit procedure, looking for wins that didn't come from the work (decision 5a). Its output is the clean solve rate on the dashboard. It never feeds the reward, but a confirmed hack it finds pauses the run (stop rule 5). Spec v2 adds edit wins to its sample: does the change fix the task, or pass the tests some other way?

  







  

    
09 · CHANGING CODE
Edit episodes: the model changes a repository

    
Built and testedCosts inferred: no real model has run an edit task yet

    
Every task in the chapters so far ends in an answer: a number, a name, a list of files. The root writes Python in every one of those episodes, but only to read. On 12 Oct Rishi approved adding real code editing to the run, so the model learns to change code, not only to read it. Under spec v2, 40% of the training tasks are coding tasks, and one attempt at one of them is an edit episode. A step's 32 episodes include 12 or 16 of them: 3 or 4 of its 8 tasks, 4 rollouts each.

    
An edit episode, in four sentencesThe model gets a coding task (fix this bug, or add this feature) and a repository on disk at /work/repo. For up to 20 turns it writes Python that explores the files, asks sub-calls to read and draft, edits files, and runs the repository's own tests. Then it calls submit() with a one-line summary, which nobody grades. The host takes the diff it made, applies it to a clean copy in a fresh container, runs tests the model never saw, and scores 1 if every one passes and 0 otherwise.

edit_real · 25% of tasks
Built and tested

        
Proper engineering on real repositories

        
Real repositories with their own test suites, planned in five language groups (the language box below), with tasks of three kinds. The first round has 107 training tasks in Python, Go and JavaScript.

        
    
          
  • Bug fixes: an injected bug in the source, an issue that describes the symptom, and the existing tests it breaks. For Python and Go they come from SWE-smith, which leaves those tests visible; we hide them and re-validate every task in our own grader. For JavaScript, TypeScript, Rust and Java we inject the bugs ourselves, because SWE-smith's datasets for those languages state no licence.
    • 
          
  • Feature tasks we generate on the same images: remove a function or small feature that existing tests cover, and write the request from its docstring and those tests. The tests that fail after the removal become the hidden set. This is the kind of work Rishi does most (decision E-f).
    •

The RLM way of editing

    
A normal coding agent reads files into its own context one tool call at a time, and its transcript grows to tens of thousands of tokens. An RLM root keeps its own context small and pushes the reading into code and sub-calls. Prompt v2 gives it these steps as advice:

    
    
      
  1. Explore with code. Walk /work/repo, parse modules, search for the task's identifiers, and print a summary, never whole files.
    2. 
      
  2. Delegate reading. One llm_batch over the 10-20 likeliest files: "does this file relate to the task? Name the functions and lines." The root reads the answers, not the files.
    3. 
      
  3. Reproduce. A short script that shows the bug or the missing feature.
    4. 
      
  4. Draft. Write the change in code, or ask llm to draft a function from the code around it, splice it in, and check it parses.
    5. 
      
  5. Review. Ask llm to review the diff against the task: missed callers, edge cases, behaviour it breaks.
    6. 
      
  6. Verify, then submit. Run the reproduction and the tests that matter, summarise failures in code, and submit() once they pass.
    7. 
    

    
Taught by the environment, not paid forNone of these steps earns reward on its own. The root sees only 2,000 characters a turn, the task lists files without containing them, and higher levels grow the codebase until reading file by file can't finish in 20 turns, so searching in code and delegating become the way to win. Scoring the steps themselves would teach the model to perform them for show, the same reason the Claude audit never feeds the reward.

10 · JUDGING A CHANGE
Hidden tests, a fresh box, and a 1 or a 0

    
Built and tested

    
A read episode's answer is checked against a gold answer the host already holds. An edit episode hands back a change to a codebase, and the fair test of a change is to run it. So the host runs it, in a container the model never touched, against tests the model never saw. This chapter covers the sandbox an edit episode runs in, the grader, the reward, the new detectors, how the task pool stays useful, and the evals, as spec v2 §12 sets them.

  


  

    

      
      
    

  



  

    
  


  

    
The grader, step by step

    
    
      
  1. Take the diff. After submit or the last turn, the host takes the diff of the episode's folder against the base commit and removes the episode container.
    2. 
      
  2. Check it. Text files only, inside the repository, at most 2,000 changed lines. Changes to existing test files, any conftest.py and test configuration are stripped and fire test_tamper. New test files are dropped before the run, so they are never compiled or imported.
    3. 
      
  3. Start clean. A fresh grader container from the same image, no network, the same limits: a clean copy of the repository at its base, the diff applied, the full test suite restored including the hidden tests, and two canary tests with names drawn fresh for this episode, one that must pass and one that must fail.
    4. 
      
  4. Run and read. It runs the task's fail-to-pass and pass-to-pass tests and the canaries, with a cap of at least 600 s (more for tasks whose tests run slowly), and reads each test's result from the test runner's own report: JUnit XML, go test -json, Jest, Vitest or Mocha JSON, or cargo test's per-test lines, keyed by file or package and test name. A test missing from the report counts as failed.
    5. 
      
  5. Blame correctly. A grader that can't start, or a container killed from outside, is an infra error, out of the group. A test run that hits its cap runs once more, alone, with double the cap, so a slow disk can't fail a good answer. Only a second timeout is the model's doing: every task's real fix was validated well inside the cap, timed under full load.
    6. 
    

  


  

    
The reward: all or nothing

    
Spec v2 scores an edit episode in this order (decision E-c):

    
    
      
  1. No submit, an empty diff, or a diff that doesn't apply: 0.
    2. 
      
  2. A detector fired: 0, before the group mean, as for read episodes (H11).
    3. 
      
  3. Every fail-to-pass and every pass-to-pass test passed: 1. The episode is resolved.
    4. 
      
  4. Anything else: 0.
    5. 
      
  5. The grader or its container failed: an infra error, out of the group.
    6. 
    

    
Why binary. It is what DeepSWE, Nebius and Kimi-Dev train on, and none of the open recipes the plan studied used partial credit for edits. The alternative, half a point for the share of fail-to-pass tests passing, would leave fewer all-zero groups on hard tasks, but it also pays for half-fixes the tests happen to accept. The blind-guess idea from the read reward still holds: before training, the empty patch, a patch that deletes the target code, and a patch that stubs it to return a constant must all score 0 on every edit task kind and level.

  

  

    
  


  

    
Three new referees, and one that only takes notes

    
The four read-episode rules stay. For edit episodes, early_submit means submitting on turn 1 or before any code read a file in /work/repo; copied_answer doesn't apply; timeout_loop is unchanged; and file escapes or bridge tampering still fire escape_attempt. Three rules are new, test_tamper, grader_tamper and test_aware, and one new signal, network_try, is logged without touching the reward.

  

  

    

      
test_tamper · zero
Changing the tests
The diff touches an existing test file, any conftest.py or test configuration, or adds skip or xfail markers to existing tests. The change is stripped before grading, so it can't help, and the reward is 0 even if the rest of the fix is right.

      
grader_tamper · zero
Faking the results
The must-fail canary passes, the must-pass canary fails, the number of collected tests is off, or the report is missing or malformed. This catches a change that rewrites the test runner at import time or exits early to fake a pass.

      
test_aware · zero
Code that knows it's being tested
New non-test code reads PYTEST_CURRENT_TEST, looks for the test runner in sys.modules, imports _pytest, calls os._exit, or does the equivalent in the repository's language.

      
network_try · logged only
Reaching for the network
A blocked network attempt, such as pip install. With no network it can't gain anything, and agents often try it while debugging, so it is counted but doesn't zero the reward.

    

  

  

    
Broader signals, such as inspect.stack(), new environment-variable reads or sys.settrace in non-test code, are legitimate often enough that they go to the Claude audit's queue instead of the reward. Before any credit is spent on edit tasks, the edit environment and the grader get a red-team, as step 8 did for reading. Step E6 is the brief for it: everything else is built, and the brief is written when Rishi asks for it; he hands it to a separate Claude session himself. That session checks whether reward can be earned without solving the task: forged results, test edits, conftest tricks, history mining, reaching the hidden tests, crashing the grader. Every hole that works gets fixed and a regression test.

Keeping the task pool useful

  

  

    

      
Before a real task enters the pool
In our own grader: the real fix (the gold patch) passes every fail-to-pass and pass-to-pass test three runs in a row, so flaky tests are out; the empty patch fails every fail-to-pass test; removing the hidden test files doesn't break the visible ones; the real fix finishes in under half the grader's cap; and the task text quotes neither the real fix nor a hidden test's name. This costs PC time only.

      
Task retirement
A group whose 4 rollouts all score the same teaches GRPO nothing. So a task whose group came back all-0 twice, or all-1 once, isn't drawn again, and real tasks don't spend ~$0.60 a group on no signal. It uses training rollouts only, so it costs nothing extra, and the retirement state is saved with every checkpoint, so a resume keeps it. Levels and the controller work on top of it, as for every family.

11 · THE THERMOSTAT
Keeping every group in the zone where GRPO learns

    
GRPO learns only from groups whose four rollouts disagree. If all four pass or all four fail, every advantage is 0 and the group is dropped. In the 20-step run, trainable groups fell from 7 of 8 to 3-6 of 8 as the model improved (H13). The difficulty controller keeps each family at a level where it passes sometimes but not always. It runs the same way for the edit families, whose pass rate is the resolved rate, and real edit tasks that keep coming back all-0 or all-1 are also retired from the pool (chapter 10).

    
    
      
  • After every step, each family's pass rate (exact accuracy for a read family, the resolved rate for an edit family) is taken over its episodes from its last 3 steps at the current level, if there are at least 8.
    • 
      
  • Above 70%: up one level. Already at level 5? That family is saturated; when every family is, stop rule 4 fires.
    • 
      
  • Below 20%: down one level, never below 1.
    • 
      
  • A move clears the window, so a family waits at least 3 steps at a new level, and pass rates are never mixed across levels.
    • 
    

  

  

    
  







  

    
12 · THE UPDATE
GRPO in one picture

    
Group Relative Policy Optimization needs no value model and no judge. Each task is run 4 times from the same checkpoint (a group). Each rollout's advantage is its reward minus the group's mean. Tokens from rollouts that beat their siblings get pushed up; tokens from those that lost get pushed down. We don't divide by the group's standard deviation (scale_rewards=False), which would over-weight groups whose rewards barely differ.

  

  

    
  

  

    
What actually gets trained

    
An episode is one long conversation: the system prompt, the first message, and then alternating root turns and observations. Only the root's own tokens carry loss. Everything the environment wrote (observations, REPL output, error messages) is context, not something the model is graded on producing. Sub-call text never appears at all unless the root's code printed it. An edit episode works the same way: file contents and test output its code printed are context, and only the root's plans and code carry loss. An edit transcript should run ~15-30K tokens, and up to ~95K if every cap is hit (inferred); the step 6 rule sets the trainer's sequence length from measured lengths.

  

  

    
  

  

    
The loss: CISPO, with its clip restored

    
The loss is CISPO. Each token's update is weighted by the importance ratio between the policy being trained and the one that sampled it, clipped to [1 − ε, 1 + ε_high] = [0, 5] and treated as a constant. Unlike PPO-style clipping, no token is ever dropped from the update; an extreme one just has its weight capped.

    
A bug the spec fixed (decision 1c)The 20-step run passed epsilon = epsilon_high = 0, which forced every weight to exactly 1, so its clipped-token fraction read ~0.97 every step. Production pins ART's defaults (1.0 and 4.0) explicitly. The clipped fraction should now sit near 0, and that becomes the baseline to watch.

13 · THE MACHINE
One training step, and the rules that end the run

    
scripts/train.py runs on Rishi's PC. The sandboxes, grader and detectors run there too; W&B serves the model and does the gradient update. One step turns checkpoint n−1 into checkpoint n.

  

  

    
  


  

    
Inside one step

    
    
      
  1. Draw and roll out. 8 tasks, split so the run keeps spec v2's mix (25/10/10/15 read, 25/15 edit), each at its family's current level: generated from fresh seeds, or for edit_real drawn from the validated pool, skipping retired tasks. 4 rollouts each from checkpoint n−1: 32 episodes at once, every edit episode followed by its grader run. Each is logged as a transcript.
    2. 
      
  2. Filter. Infra episodes out; then groups left with fewer than 2 episodes, and groups whose rewards are all equal, are dropped. The controller updates, and 4 rollouts are re-scored by the base model for KL.
    3. 
      
  3. Commit spend, then train. The step's inference cost is recorded first, then the surviving groups train into checkpoint n. Fewer than 2 trainable groups skips the update, and checkpoint n equals n−1.
    4. 
      
  4. Log. The step's metrics go to results/<run>.json and W&B: pass rates, levels, reward parts, detector hits by rule, entropy, KL, clip fraction, grad norm, sub-calls, turns, tokens, cost and timing, plus the edit block for edit episodes (chapter 09).
    5. 
      
  5. Between steps. Any due eval runs (every 10 steps), the audit sample is written at every 10th checkpoint, checkpoints are kept or pruned, then the loop checks the infra pause, the collapse rule, the five stop rules, the step limit, the STOP switch, and whether the next step fits under the spending ceiling.
    6. 
    

  


  

    
  


  

    
How the learning rate is chosen, and how it backs off

    
The 20-step run used 1e-5. Production might learn faster at 2e-5, but a too-high rate can make the policy collapse. So the second seed earns the right to the higher rate, and production keeps a safety net.

  

  

    
  

  

    

      
Checkpoints kept
0 (the base), every 5th, every evaluated one, the best and the latest. The rest are deleted from W&B (--no-prune keeps them). Each kept one saves the pinned config: ART version, model, chat template, prompt version and hashes, limits, train arguments, LR branch, data manifest hash, controller state, task retirement state, git commit and spend.

      
Resume
From the latest checkpoint, or from any earlier kept one, which forks it into a new branch so nothing is deleted; later steps' logs move to abandoned/. Spend never rolls back. Forking on W&B is untested; a one-step check (~$0.50) at step 10 is Rishi's call.

    

    
Step 6 shipped with 214 tests against fake backends (213 pass, 1 skip) at $0. A dry run did 42 steps in 34 seconds.

On the PC's USB drive a step should take about 30-35 minutes, against 290 s for a read-only step, so the run takes about 40 hours (inferred from timing the first round's tasks under load). The slow drive costs time, never reward. The first round's 107 training tasks are fewer than the ~150 edit_real draws such a run makes, and retiring used-up tasks shrinks the pool further, so step 12 settles that before it starts.

        
Watch for: reward std falling off a cliff, entropy dropping fast or KL jumping, sub-calls climbing toward 30 without accuracy following, turns or tokens at their caps, infra errors above 1%. For edits: episodes at 20 turns with tests still failing, repeated cells, empty diffs, and the resolved rate rising without the testing and sub-call habits that should come with it.

      

    

  

  

    
What a healthy production run should look like

    
With a difficulty controller, training reward is not supposed to climb smoothly. Each time a family moves up a level its tasks get longer and harder, and its pass rate drops back before it climbs again. A sawtooth in training reward is the controller working; the selection set, which never changes, is where real progress shows.
